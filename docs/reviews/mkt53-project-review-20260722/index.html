06 / ARCH

当前架构与目标架构

当前系统的优势是静态、可回退、发布简单；限制是没有身份、业务状态写入、共享查询层和实时数据面。目标架构应保持静态前端，同时增加最小后端而非一次性重写。

当前

静态证据前台

  • React 19 + TypeScript + Vite 8 + HashRouter。
  • 页面数据主要来自 TypeScript 静态数组与 public/periodic-data JSON。
  • 半月脚本构建 manifest、connector backlog 与 source task queue。
  • nginx 托管静态文件；宿主 landing 与 mkt53 分离发布。
  • 无登录身份、RBAC、数据库状态机、报告任务、AI provider proxy。
目标

可复核决策平台

  • 静态前端继续负责高性能展示。
  • Backend API 负责身份、权限、review、snapshot、report job 与 AI proxy。
  • PostgreSQL 保存 registry、快照元数据、review log 与 action lineage。
  • Object Storage 保存原始导入、报告和 AI 资产。
  • 连接器按 source contract 进入 staging，不直接改前端源码。
  • BE-01 已决定同机独立 Compose + edge/data 双网络；共享 nginx 只承担同源 API 入口。

07 / RETRO

完整项目复盘

项目的关键进步不是页面数量，而是从品牌迁移逐步长出了工程门禁与证据治理；当前停滞点同样清晰：前端与脚本继续膨胀，但后端产品能力没有同步形成。

做对了什么

  • 统一 Momcozy 品牌与“五看”信息架构。
  • 41 个 lazy route component，降低首屏一次性加载。
  • 页面证据 gate、source registry 与 deep audit 相互约束。
  • 全路由桌面/移动 E2E 检查证据文案、溢出和 console error。
  • 静态发布、smoke 和 production E2E 有明确边界。

为什么开始变慢

  • DataManage.tsx 已从 2,487 行降至 641 行，但 SelfInsight 1,103 行、UsersPage 987 行仍偏大。
  • 静态目录已拆分，后续仍需把治理元数据迁到可版本化 API。
  • 数据脚本已形成 80+ 命令，owner 流程以批次脚本累积。
  • “verified”与“可展示事实”仍存在字段缺省的历史兼容层。
  • 通知、搜索、语言和用户头像多为前端静态状态。

根因

  • 以页面交付替代领域模型和后端状态机。
  • 连接器授权与业务 owner 证据长期缺位。
  • 缺少产品使用遥测，无法验证“效率、ROI、决策影响”。
  • 静态看板被迫承担 catalog、governance、workflow 三种职责。
  • 依赖安全曾从 0 回归到 14 high，说明版本下限和旧导入也必须成为永久合同。

应停止 / 应继续 / 应开始

Stop

停止新增无法追溯的数字、静态“实时通知”、批次编号式 UI、没有快照 id 的报告和 AI 效率宣传。

Continue

继续 evidence gate、source registry、deep audit、HashRouter 生产约束、local/prod 验证分层和 fail-closed connector readiness。

Start

开始后端最小闭环、RBAC、snapshot/review 状态机、模块级 owner SLA、使用遥测和依赖安全响应。
